# 稿流比赛录屏介绍视频：脚本生成提示词

你是一名擅长比赛路演、产品演示、录屏剪辑和中文人工智能配音脚本的编导。请为我们的比赛项目“稿流 Open Publisher Web”编写可直接拍摄、剪辑、分段配音的录屏介绍视频脚本。

注意：任务是编写脚本，不是执行真实模型调用或对外发布。

## 一、成片目标

- 总时长十到十二分钟，优先按十一分钟，即六百六十秒设计。
- 必须介绍独立管理端和客户端，并完整呈现同一次真实生成到发布的操作。
- 管理端讲清平台如何配置和管理；客户端讲清用户如何完成内容任务。不要机械遍历菜单。
- 以一次真实的产品更新推广任务为主线，输入资料、生成稿件、修改版本、确认配图、同步草稿、平台确认发布前后对应。
- 视频允许剪辑。不设置等待段、不预留生成缓冲时间，也不安排无意义的加载画面。模型生成、图片生成和同步等待可以剪去或加速；保留真实触发、关键过程和结果，并在相应画面标注“等待已剪辑”或“过程已加速”。
- 剪辑不等于实际耗时缩短。不得把剪辑后的片段长度宣称为真实生成耗时，不得混用其他稿件的结果。

## 二、项目事实与表达边界

项目名称：稿流，英文名 Open Publisher Web。口播优先只说“稿流”。

一句话定位：面向产品推广与内容运营的人工智能图文创作及发布工作台。这里的“推文”包含平台推广图文，不限定短文本，界面以“文章”管理稿件与版本。

目标用户：独立开发者、产品创作者和中小团队内容运营人员。

核心痛点：产品资料、写作、配图、修改和发布分散在不同工具中；资料依据容易丢失；多次修改难以追溯；发布前缺少明确确认。

解决方案：围绕同一份稿件，将资料研究、大纲规划、正文生成、编辑、配图、版本留存和平台草稿同步组织在工作台中。

三个核心亮点：
1. 创作有依据。资料研究、结构规划和流式正文按阶段推进，展示实际来源与检查结果。
2. 修改有记录。人工编辑和人工智能修改保留修订，配图由用户确认后应用。
3. 运营可管理。独立管理端提供账号、模型配置、用量、价格及审计管理，用户掌握最终发布确认。

管理端已具备：
- 成员与管理员账号目录、角色和状态筛选、新建账号、启停用、调整角色、重置密码。
- 用量概览与明细，包括调用、令牌、图片、状态、延迟和单价快照。
- 模型价格配置与估算成本。没有匹配价格时显示“未计价”，不得编造成真实账单。
- 安全审计，以及独立分区的模型配置。具体模型种类和页面字段以实际录屏为准。
- 模型及集成密钥经后端加密保存，前端不回显明文；演示只展示已配置状态，不录入或展示真实秘密。

客户端已具备：
- 创作入口、稿件列表、编辑工作台、模板库、素材库。
- 资料输入、分阶段创作、流式正文、编辑助手、修订历史与恢复。
- 智能配图、素材上传、图片拖入正文与预览，配图确认后应用。
- 同步前风险检查，以及通过浏览器文章同步助手同步到目标平台草稿箱。

真实发布边界：
- 客户端“同步发布”通过浏览器扩展连接已登录平台，将内容同步到平台草稿箱。最终公开发布由用户在目标平台确认。
- “同步完成”“草稿已保存”“公开发布成功”是三个不同状态，口播必须与实际证据对应。
- 发布段应安排：同步前检查 → 人工确认 → 选择实际平台 → 同步状态及回执 → 打开平台草稿 → 核对图文 → 平台确认发布 → 查看实际发布结果。
- 目标平台、账号授权、发布权限及链接尚未确认，标记【待补】。可以在脚本安排真实操作，但不得写成已经完成。若拍摄条件只支持草稿同步，明确标记【待补：公开发布验证】，不能称为完整公开发布成功。
- 不将后端独立 Outbox 接口描述为当前客户端插件同步使用的队列，也不演示已移除的独立模拟发布队列页面。

技术表述边界：
- 日常工作台主线采用 WriterService 和 RunJournal 组织创作、运行事件与修订。
- 另有 LangGraph 候选生成、评分与循环改写链路。不得把客户端所有创作过程都说成该候选链路，不得把未录制的节点当成已演示。
- 技术名词用在解释可见行为时，不用长时间堆砌架构术语。

已有工程证据：截至二〇二六年十月三十一日，项目验证记录记载三百三十四项后端测试通过，客户端与管理端构建通过，并有主要浏览器操作验证。该结果来自隔离测试及模型替身，不等于真实模型效果、第三方平台发布成功率或商业成果。本次真实演示结果必须另行取证。

团队人数、成员分工、比赛正式名称与赛道、用户规模、商业收入、效率提升、生成质量指标及知识产权资质：均为【待补】，不得自行编造。

结尾记忆点建议：从产品资料到发布内容，每一步都能确认与追溯。

## 三、建议章节节奏

以下为成片时间，已经包含口播、点击、画面阅读及转场，不另加等待预算。可以微调，总时长必须为六百至七百二十秒。

| 时间码 | 内容 | 任务 |
|---|---|---|
| 00:00—00:20 | 钩子与结果预告 | 前三秒点出痛点，展示实际图文结果；若使用后拍结果，标记结果预览 |
| 00:20—01:05 | 痛点与用户 | 用产品更新推广场景说明工具切换、事实和版本问题 |
| 01:05—01:50 | 方案与亮点 | 介绍稿流定位和三个核心亮点，建立双端关系 |
| 01:50—03:45 | 管理端 | 模型配置、账号、用量、价格、审计；每处都解释用户价值 |
| 03:45—04:45 | 客户端 | 创作、稿件、模板、素材和工作台，为同一任务选择入口 |
| 04:45—08:30 | 真实生成与编辑 | 输入事实、触发真实模型、展示过程与结果、修改、版本、配图和预览 |
| 08:30—10:10 | 真实发布操作 | 检查、同步草稿、平台核对与确认发布、验证最终状态 |
| 10:10—10:45 | 证据与进展 | 可回看本次调用记录，并区分工程验证与真实演示成果 |
| 10:45—11:00 | 结尾记忆点 | 回到用户价值，给出一句简明可信的收尾 |

## 四、真实演示的分镜要求

1. 全片围绕同一条稿件和同一个推广目标，不频繁更换无关案例。演示主题、资料与目标平台未确定时用【待补】，不要捏造产品事实。
2. 管理端展示已配置的真实模型档案。客户端采用该真实服务生成，禁止用固定响应、预置示例或模拟服务冒充真实调用。公共示例可用于介绍页面，必须注明示例，不能当成本次生成结果。
3. 触发生成前明确输入：产品事实、目标读者、传播目标、语气和目标平台。输入内容可提前准备，拍摄时粘贴，无须逐字录入。
4. 保留点击生成、可辨认的运行反馈、流式正文片段、完成状态和结果阅读。等待直接剪辑，操作顺序及稿件对应关系必须真实。
5. 展示一次有明确目的的修改，例如删去无依据的宣传承诺。修改指令须基于真实稿件，不预言模型必然输出的措辞。
6. 展示保存及版本对比或恢复，说明当前版本。需要恢复时不得破坏最终准备发布的稿件，可恢复后再保存确认稿。
7. 展示配图方案、用户确认、实际可用素材应用和正文预览。真实生图尚未确认时标记【待补】，不能把上传图片称为现场生成图片。
8. 风险检查展示本次真实状态，不编造高风险命中，不把规则检查说成平台合规保证。
9. 发布步骤依赖真实账号与平台条件，给出待取证画面及未成功时的诚实替换说法，不把失败画面剪成成功。
10. 能按稿件、时间和模型关联时，回看管理端本次真实调用记录；无法准确关联时只介绍记录能力，不能把其他调用归为本次。
11. 每个分镜写清页面、按钮或操作、应出现的可见结果、剪辑点。未知按钮名称标记【待核对】，不要杜撰。
12. 只展示必要页面，隐藏账号敏感信息、登录令牌、完整密钥、私人资料及未公开数据。

## 五、口播与音频规范

1. 开头三个钩子备选各不超过二十字；推荐钩子的首句不超过十二字，适配前三秒。
2. 口播正式、自然、有吸引力，不夸张营销。每句不超过十八个实际发音字，一段最多三句。
3. 以五至八秒为一个独立配音段。章节可以包含多个配音段，禁止把一整分钟写成一个配音单元。
4. 普通话按每秒约四个实际发音字估算。字数统计排除标点和停顿符号；数字和英文按转换后的读法估算。短停顿建议约零点二秒，长停顿约零点五秒，以实际试听校准。
5. 用“/”表示短停顿，用“//”表示长停顿。每个配音段可单独试听、重配，必要时重复对象名称，避免“这个”“刚才”等指代不清。
6. 数字、英文缩写及易误读术语，在“音频校准备注”中列出读法。口播优先使用自然中文，不强行朗读内部类名。多音字按具体语境注明读音。
7. “TTS纯文本版”中把数字和英文转换为实际朗读文本，不包含括号、读法说明、序号、时间码或章节名。每段一行，顺序和分镜编号严格对应。
8. 口播与字幕分开。字幕精简但含义一致，产品界面中的英文或阿拉伯数字可以保留。
9. 片段时长等于配音与操作并行后的实际占用时间。需要读图或点击时明确停留，不把口播时间和同时发生的操作时间重复相加。不得为填满时长扩写空话。
10. 用最终时间码合计核验成片在十到十二分钟内；单列口播估算和无口播操作停留。不得通过反复朗读加载状态补时。

禁用表达：本轮、这一轮、上一轮、接下来我们、好的、那么、大家可以看到、如你所见、让我们、镜头给到、这里我、废话不多说、众所周知、赋能、闭环、生态、颠覆、引领、极致、一站式。避免连续使用“首先、其次、最后”。不写直播或对话残留。

## 六、按顺序输出

1. 三个开头钩子备选，并推荐其中一个。
2. 推荐的一句话价值主张。
3. 章节时间表，注明管理端、客户端、真实生成、发布各占多少时间，核验合计。
4. 完整分镜脚本表格，列为：序号｜起止时间码｜画面/操作及预期结果｜口播文本（带停顿）｜屏幕字幕｜片段时长｜音频校准备注｜剪辑与取证要求。每行对应一个独立配音段，不遗漏中间段落。没有口播的必要操作停留单独标记，并纳入时间码。
5. 单独输出“TTS纯文本版”，每段一行，与分镜逐段对应。所有【待补】必须在正式配音前补齐，不把占位符直接送去配音。
6. 简明拍摄检查清单：真实模型配置、测试账号、输入资料、模板素材、插件与平台登录、发布权限、隐私遮挡、图文结果和发布取证。
7. 自检清单：总时长、章节合计、每段秒数、逐句字数、数字与英文读法、纯文本对应关系、禁用词清零、双端覆盖、同一稿件贯穿、真实调用、发布状态区分、剪辑标记、数据证据和待补项。检查发现不符合先改稿，不要只声称全部通过。
8. 最后列出最多三个需要补充的问题，优先询问：比赛名称及赛道、真实演示主题及可用资料、目标平台及能否展示公开发布结果。其余缺失信息先用【待补】占位，不因信息不足停止输出脚本。
